# 电费采集与数据模型

## 目的

说明真实电费快照的查询、保存、去重与用户级自动采集。本文不涵盖演示数据，演示数据只用于展示读取。

## 采集入口

- 浏览器手动查询：`POST /api/v1/electricity/query`。
- 当前用户手动测试采集：`POST /api/v1/electricity/collection/run`。
- Scheduler：每日枚举启用且宿舍配置完整的用户，调用相同的 `CollectionService.run_once(user_id)`。

宿舍选择所需的校区、楼栋、楼层、宿舍列表来自当前用户的已认证 BUPT Runtime Client。不会扫描或批量枚举无关宿舍。

## 保存模型

`ElectricityService.query_and_save()` 请求上游后，将标准化 `ElectricityReading` 保存为 `electricity_records`。保存 `source_time`、查询时间、余额、剩余电量、累计用电和原始上游字段。

若 `(area_id, room_id, source_time)` 已存在，返回成功结果并标识 `duplicate=true`，不会重复插入。这表示查询本身成功但上游还未产生新的日结数据，不是数据库故障。

## 自动采集状态

用户 `collection_settings` 保存：

- 当前宿舍定位与名称；
- 是否启用；
- `last_attempt_time`、`last_success_time`、`last_source_time`；
- `never_run`、`success`、`no_room_configured`、`not_authenticated`、`session_expired`、`upstream_not_updated`、`failed`、`already_running` 等状态。

同一用户的 CollectionService 使用进程内 `asyncio.Lock` 防止手动运行与定时任务并发访问同一上游宿舍。

## 安全与运行注意事项

- Scheduler 只读取用户作用域 `collection_settings`，不读取 legacy unassigned 表。
- 没有有效 Runtime Session 时跳过查询，不自动重新登录。
- 真实采集链不接受 Demo Provider 替换：`Scheduler → CollectionService → ElectricityService → ElectricityRepository → electricity_records`。
